# 技术方案

先消费 [项目上下文](../dtc-context/SKILL.md)，写作遵循 [文档规范](../dtc-documentation/SKILL.md)。输入是已知需求、真实代码及约束，不要求为后端设计补 UI 资料。

1. 沿实际调用方定位路由、服务、Graph、工具、仓储和外部接口，区分已有行为与目标行为。状态字段存在不等于状态已持久保存。
2. 比较真实可行方案：继续使用、局部扩展、替换或新增。写清业务正确性、维护量、可学习性、可验证性、迁移代价和未知项。没有证据不打虚构总分；说明什么新事实会改变选择。
3. 按范围定义职责、输入输出、数据归属、认证授权、状态迁移、失败处理、旧调用方兼容与撤回方法。拟新增文件/接口显式标为计划。
4. 涉及写入时分别回答：谁批准、批准针对哪些参数/版本、重启从哪里继续、重复请求如何识别、外部结果未知时如何处理。数据库事务不能回滚已经发生的外部操作；租约不能撤销已发出的请求。
5. 把需求对应到改动和验证：行为 → 文件/函数 → 测试场景 → 预期结果。尚未执行的验证只写预期，不填写成功计数。

小改动用短段落，独立复杂模块才建立设计入口或重大决策记录。沿用现有分层，不为满足模板重排仓库或引入新平台。

交付前检查推荐方案、未选原因、代码事实、假设和待决项是否可分辨。使用 [有边界的审查](../dtc-scoped-validation/references/independent-review.md) 复核用户要求审查或有实质风险的方案；自查不冒充独立审查。已有授权范围内交给 [实现](../dtc-implementation/SKILL.md)。
