# 文档设计与学习

本技能移植 Hextech 的文档归属、唯一权威入口、技术契约与证据分层原则，结合当前项目已有源码教学结构。已去除品牌、店铺、私有平台和多应用运行约定。

先读 [项目文档规范](../../../docs/guides/documentation.md)，再读同主题现有文档；本规范是人读正本，本 skill 负责执行入口。首次了解接入选择时读 [技能指南](../../../docs/guides/skills.md)。

## 写作过程

1. 判断读者现在要回答什么：业务目标、设计原因、实际操作、学习概念或验证结果。只修改对应权威文档；小修正补原文，不生成整套空模板。
2. 以内部客服处理一张工单的具体问题开头。首次出现的新词给一句中文解释和项目例子，必要时类比前端经验，并说明类比边界。
3. 讲清输入、处理、输出与失败情况，再介绍技术实现。已有能力给真实文件/函数锚点；计划能力明确标注，示意代码不能冒充已有代码。
4. 对重要设计比较真实可行选项，解释选择、代价、未选理由与改变决定的条件；“更复杂/更流行”不等于更适用。
5. 学习说明按问题 → 概念 → 源码 → 取舍 → 失败例子 → 小实验与预期 → 自检组织，规模可裁剪。预期与实际结果分开，不让读者先掌握整套算法才能开始。
6. Markdown 为正文；图有益时用 Mermaid，并给文字版解释。避免只靠图片编号、颜色、截图或外部页面才能理解正文。HTML 展示需要独立需求与维护理由。
7. 运行 `python3 scripts/check_project_docs.py` 和 `git diff --check`；人工核对术语、状态、源码与证据。结构校验不证明文档语义或业务行为正确。

交付时告诉读者先读哪一篇、可以学到什么、哪些能力还未实现。实质新增学习或设计文档时使用 [可读性与设计检查](references/review-checklist.md)。
