# 文档可读性与设计检查

先读当前需求和具体 diff，按范围检查，不要求每篇文档满足所有类型的模板。

- 新读者能否先说清谁在使用、解决什么问题、输入与结果是什么？
- 专业词第一次出现是否有中文解释和售后例子？前端类比是否隐去了服务端权限、并发或持久性差异？
- 能否区分上游已有、本 fork 新增、拟实现、仅静态核查和实际运行结果？
- 每个核心行为能否定位到真实函数或明确计划的模块？描述是否超过代码能保证的范围？
- 设计比较是否基于当前约束，有未选理由和改变决定的条件？是否引入无当前需求的基础设施？
- 实验是否写清前提、动作、可观察预期和判断方法？依赖缺失或收费操作是否提前说明？未执行是否明确？
- 目录、源码、验收和事实记录是否互链？是否又新建了另一份“最新方案”？
- 去掉截图和 Mermaid 渲染后，文字是否仍可理解？是否含本地绝对路径、内部链接或未经脱敏数据？

结果写具体位置、问题、影响和最小修正；无发现也说明范围。优先修正事实错误和学习障碍，不把个人排版偏好当阻断问题。审查与实际运行测试分别记录。
