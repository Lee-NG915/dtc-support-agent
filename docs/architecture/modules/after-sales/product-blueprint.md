# AI 辅助售后客服工作台：完整产品文档

更新日期：2026-11-04

状态：**产品决策已确认；应用尚未实现**。

本文是跨仓库 AI 辅助售后工作台的**产品与交互正本**。文中的页面、状态迁移、接口行为、验收场景和发布安排均为已确认的计划，不代表已经开发、联调或通过验收。实施记录和实测结果应另按项目文档规范归档，不能用计划代替验证。

## 1. 这份文档回答什么

消费者收到一张破损的餐桌后，通常要在订单页说明问题、上传照片，再等待客服查订单、查物流、核对退换政策并创建售后工单。对客服来说，麻烦不只是在聊天框里生成一句话，而是确保：这是本人的订单、适用的是这一版本的政策、批准的是这一版处理方案、重复点击不会生成两张工单、网络超时后也能查明外部结果。

一句话定义本产品：**E-pig 提供消费者订单与售后入口，DTC Support Agent 提供内部客服工作台；AI 负责查资料和写草稿，确定性规则负责权限与业务校验，人负责每一次正式工单写入的批准。**

本文统一回答以下问题：

- 为什么做、首期做到哪里、明确不做什么；
- 消费者、客服、审批人和两个系统分别拥有什么权限与数据；
- 一条诉求怎样从提交走到唯一工单和唯一消费者回复；
- 缺资料、审批驳回、版本过期、重复请求、服务重启和外部超时时怎样处理；
- 五个关键页面在加载、空数据、无权限、失败、陈旧、冲突、重试和成功时怎样表现；
- 哪些需求与验收编号可追踪到阶段及负责仓库。

跨仓 HTTP 的集成语义见 [E-pig 售后对接契约](epig-contract.md)。线路 Schema、字段类型、序列化与契约示例只在 [OpenAPI v1](../../../../contracts/epig-after-sales/v1/openapi.json) 维护，本文不复制一套字段定义。附件、轮询、回复和审批权威均按本文 2026-11-04 的产品决定执行，不再作为开放问题。

阅读顺序建议：**本文背景与完整旅程 → 状态机与页面行为 → 需求及验收映射 → 集成语义 → OpenAPI Schema**。项目总体工程边界仍见 [项目方案](../../../project-plan.md)。

## 2. 背景、目标与非目标

### 2.1 当前基础与真正要补的能力

当前 DTC 仓库已有上游问答演示页，以及政策检索、路由、引用、工具调用和护栏等可复用内核；也有进程内待确认动作等演示基础。这些能力可以帮助客服“找到依据、形成建议”，但还不等于可恢复的售后业务系统。当前聊天页中的 `user_id` 请求参数也不是可信身份。

E-pig 已有消费者订单体系、订单详情页和订单归属凭据。本产品复用这些既有条件，不为售后另建消费者账号，也不在 E-pig 内嵌一套客服后台。

| 已有、可复用的基础 | 本期计划新增的工作台能力 |
|---|---|
| 内部政策问答、混合检索、引用与忠实度检查 | 带政策版本和证据快照的工单草稿 |
| 工具注册、路由与演示订单查询 | 受服务令牌和市场范围约束的 E-pig Connector |
| 问答聊天页与流式输出 | 诉求队列、诉求/工单详情、审批中心 |
| 进程内确认雏形、局部幂等基础 | 跨重启持久审批、业务操作账本、恢复与对账 |
| E-pig 订单详情和消费者订单归属体系 | 售后申请入口、私密附件、诉求与工单进度、唯一回复 |

因此，“保留政策聊天”不等于“已经有售后工作台”，“AI 能写一段答复”也不等于“有权创建工单”。

### 2.2 产品目标

1. **让客服在一个上下文中完成判断。** 在同一详情页看到订单、物流、私密凭证、政策版本、AI 建议和草稿，减少跨页抄写。
2. **让每次正式写入都可解释。** 每张工单都对应一个持久人工批准，批准绑定具体草稿、订单状态和政策证据版本。
3. **让重复和失败不制造第二个业务结果。** 消费者诉求提交、DTC 执行和 E-pig 工单创建均有幂等语义；未知结果先查询和对账。
4. **让消费者得到明确而克制的反馈。** 消费者能提交诉求、看到处理进度，并在工单创建后看到唯一、不可变的最终回复。
5. **让权限、审计和恢复成为主流程的一部分。** 跨市场访问、未审批写入、陈旧审批和无法确认的外部结果都不能被界面“乐观成功”掩盖。

业务收益不预设提升百分比。后续试用应分别记录处理时长、草稿修改、审批退回、重复拦截、对账耗时和消费者可理解性，再与人工基线比较。

### 2.3 MVP 非目标

首期明确不做：

- 消费者多轮 AI 售后聊天、自动追问或在线补聊；
- AI 自动批准、自动创建工单或绕过人工的“低风险直连”；
- 真实支付退款、自动取消订单、自动执行退货物流或补发；
- E-pig webhook 推送、新消费者账号体系、新审批系统或 JWS 审批签名体系；
- 一个诉求对应多张并行工单、工单创建后的追加/编辑消费者回复；
- 全品类商城、营销选品、通用工作流搭建器、多 Agent 团队或模型微调；
- 默认接入真实客户数据，或向任意第三方承诺分布式 exactly-once。

“创建 action 为退货、退款或补发的工单”只是记录经批准的售后处理决定，**不代表钱款已经退回、订单已经取消或商品已经发出**。真实业务执行仍由既有线下或上游流程承担。

## 3. 参与者与角色/市场权限

### 3.1 身份和市场如何生效

- **消费者**继续使用 E-pig 已有的签名购物车会话与订单归属凭据，不要求为售后额外注册或登录。E-pig 验证签名、有效期和路径市场，从已验证的 `cart_id` 得到稳定消费者主体，再检查订单、诉求、工单和附件与该主体的持久关联；仅 Cookie 合法或订单号相同市场的组合不构成授权。浏览器不能通过改请求里的用户编号访问他人订单，消费者幂等作用域使用稳定 `cart_id`，Cookie 续期不能制造重复诉求。
- **DTC 与 E-pig 的服务间调用**使用服务端 Bearer token，并同时校验调用的市场是否在该服务配置的允许列表中。token 只存在服务端，不下发消费者浏览器，也不能代替消费者订单归属校验。
- **内部员工**由 DTC 服务端确认身份，再按员工角色和允许访问的市场列表授权。`au`、`sg`、`us` 等市场逐一配置，默认无权限；“有客服角色”不等于“能看所有市场”。
- **AI**没有独立业务身份，不能提升自己的工具权限，也不能成为审批人。

所有列表、详情、附件内容、审批、事件和重试都要重新应用同样的角色/市场检查。隐藏按钮只是界面提示，不是授权边界。

### 3.2 权限矩阵

| 参与者 | 允许的工作 | 明确禁止 | 市场范围 |
|---|---|---|---|
| 消费者 | 在本人订单提交诉求；读取本人诉求、工单进度、本人附件和最终回复 | 看他人订单/工单；持服务 token；调用内部审批或重试接口 | 由本人订单所属市场决定 |
| 客服 | 查看诉求队列、订单/物流服务视图和授权附件；生成与编辑草稿；提交审批；查看回执和审计 | 批准工单；绕过审批直接创建；访问未授权市场 | DTC 员工角色 + 市场列表 |
| 审批人/主管 | 查看待审批版本及依据；批准或内部驳回；查看执行结果 | 修改已锁定审批版本；用旧批准执行新草稿；越市场审批 | DTC 审批角色 + 市场列表；发起与批准权限分离 |
| 只读审计员 | 查看授权范围内的草稿、审批、状态历史、操作和对账记录 | 修改草稿、批准、创建工单或改变游标 | 显式审计角色 + 市场列表 |
| 运维/对账人员 | 查看脱敏运行信息；在授权范围内推进对账、登记人工核验结果 | 伪造审批或回执；把未知结果直接标成成功；默认浏览完整 PII | 显式运维/对账角色 + 市场列表 |
| DTC 服务 | 轮询诉求；查询订单/物流；在有效批准后以稳定幂等键创建或查询工单；保存内部过程 | 自行产生“人工批准”；使用未配置市场；将内部笔记发给消费者 | 服务 token + DTC/E-pig 两侧允许市场配置 |
| E-pig 服务 | 校验消费者归属；持有诉求/工单；校验服务权限；幂等建单；提供授权附件内容和回执查询 | 代替 DTC 判断人工批准；另建审批流；接受跨市场读取 | 路由市场与服务允许列表一致 |

首期界面按客服和审批人分权。即使某账号未来同时拥有多个角色，审批接口仍须执行明确的授权策略，不能因“能打开页面”就默认可批准。

## 4. E-pig 与 DTC 的数据所有权

两个仓库通过版本化 HTTP 契约协作，**不共享数据库**。谁拥有数据，谁负责该数据的业务真相和持久约束；另一方保存必要引用、快照或处理记录，不能反向覆盖。

| 数据 | 权威拥有者 | 另一方可以保存什么 | 一致性规则 |
|---|---|---|---|
| 消费者账号、订单归属、订单与物流 | E-pig | DTC 保存处理所需的脱敏服务视图和版本/查询时间 | 执行前以 E-pig 当前业务状态复核，不以旧快照代替 |
| 消费者诉求及原始附件 | E-pig | DTC 保存诉求引用、内部处理状态和处理备注 | E-pig 的诉求标识是去重依据；附件内容须授权读取 |
| 正式售后工单、回执、消费者进度和最终回复 | E-pig | DTC 保存工单引用、已核验回执和展示状态 | 未读回或核对成功前，DTC 不宣称建单成功 |
| 员工角色、市场授权、持久游标 | DTC | E-pig 只保存服务允许市场配置 | 员工权限变化会使相关批准失效或在执行时拒绝 |
| 政策证据、AI 草稿及版本 | DTC | E-pig 在工单审计信息中保存实际使用的草稿版本标识 | 批准和执行必须指向同一草稿版本 |
| 人工审批 | DTC，且 DTC 是唯一审批权威 | E-pig 保存随工单带来的审批/草稿版本审计字段 | E-pig 不实现第二套审批状态机，不引入 JWS |
| 操作账本、重试、对账和内部审计 | DTC | E-pig 保存自身接收、幂等和工单审计 | 两边以操作/工单标识和回执核对，不共写数据库 |

E-pig 保存审批/草稿版本审计字段，是为了回答“这张工单按哪一版决定创建”，不是把审批权转移给 E-pig。DTC 保存订单快照，也不能把已变化的订单强行视为未变化。

## 5. 完整用户旅程

### 5.1 正常主旅程：从破损照片到唯一工单

1. **消费者从本人订单进入。** 在 E-pig 订单详情页选择“申请售后”，填写问题类型和描述，最多上传三张凭证图片。页面在上传和提交时说明限制，不先把不可用的文件假装上传成功。
2. **E-pig 接收诉求。** 服务端校验订单归属凭据、市场、附件和请求幂等。合法提交返回同一诉求；消费者看到“已提交，等待处理”，而不是 AI 自动结论。
3. **DTC 拉取新诉求。** Worker 按市场轮询 E-pig 的稳定诉求 feed。E-pig 只发布连续已提交高水位以下的记录，保证后到的低序号不会落在已发放游标之后；DTC 每批诉求持久化并去重后，才推进数据库中的游标。每个非空页都返回下一游标，末页也不例外；浏览器是否在线不影响拉取。
4. **客服打开诉求。** 队列展示市场、问题类型、处理状态和最近同步时间。详情页通过授权服务视图读取订单和物流，并在需要时读取私密附件内容。
5. **AI 准备材料，规则守住边界。** AI 汇总消费者描述、订单和物流，检索带版本的适用政策，给出引用、处理建议、工单动作和消费者回复草稿。规则检查订单状态、时间窗、市场、必填材料和动作合法性。
6. **证据充分才进入待审批。** 客服核对引用，修改草稿并选择补发、退货、退款、其他或业务拒绝等动作。提交审批后，这一版草稿被锁定；再修改会生成新版本，而不是悄悄改变已批准内容。
7. **审批人作出持久决定。** 审批中心展示订单、动作、金额相关后果、政策版本、附件、完整消费者回复和版本差异。审批人批准或内部驳回，决定写入 DTC；等待期间服务重启不会丢失。
8. **系统在执行前再检查。** DTC 再验员工/审批权限、市场、请求状态、草稿和审批版本、审批有效期、关键订单状态、政策证据及幂等参数。任何实质变化都使旧批准失效并回到草稿处理，不调用 E-pig 写接口。
9. **E-pig 幂等创建唯一工单。** 所有工单动作，包括 `reject`，都必须经过上述批准。E-pig 在同一数据库事务内核对当前订单版本和业务条件，以 `(market, request_id)` 唯一约束锁定一诉求一工单，同时保存工单、唯一回复、回执、幂等记录，并把诉求从 `pending` 推进到 `ticket_created`。订单版本已变化返回冲突；重复或并发提交返回原对象的当前视图，同键不同内容发生冲突，不覆盖第一次结果。
10. **DTC 读回并核对回执。** 能取得工单编号时按 ID 查询；结果未知时按稳定幂等键查询。只有确认 E-pig 已创建后，DTC 才把诉求标为已完成并展示工单编号。
11. **消费者看到进度和唯一回复。** E-pig 订单页展示工单状态与创建时写入的最终回复。回复不可追加、编辑或删除；同一诉求在 v1 不再生成第二张工单或第二条“最终回复”。

这里的“诉求已完成”指**正式工单已创建并核验回执**，不等于实物退货、补发或退款已经履行完毕。

### 5.2 异常与替代旅程

| 场景 | 系统应该怎样走 | 用户看到什么、绝不能发生什么 |
|---|---|---|
| 非本人订单、跨市场或 token 无效 | E-pig 或 DTC 在服务端拒绝，审计拒绝原因 | 不泄露订单是否存在及其中的 PII；不能靠修改市场参数绕过 |
| 重复提交消费者诉求 | 同键同内容返回原诉求的当前视图；同键不同内容返回冲突 | 页面恢复原进度或提示刷新，不出现两张诉求；旧响应不能覆盖更新后的状态 |
| 附件过大、类型不符或读取者无权 | 指出具体文件问题并允许移除/重试；内容读取单独授权 | 不静默丢弃附件，不生成公开链接，不把附件字节写进日志 |
| 订单号缺失或描述为空 | E-pig 在入口拒绝 malformed 请求，页面标出必填项，不创建诉求 | 不把一个格式不完整的请求送进 DTC，也不伪造诉求编号 |
| 已受理但必要凭证不足 | 诉求进入 `needs_info` 内部处理，等待客服线下跟进 | 不创建“先试试看”的工单，不伪造政策依据或消费者补充消息 |
| 政策缺失、版本冲突或 AI 不确定 | 保留在补资料/人工处理路径，由人补充判断后形成新草稿 | 不用语言流畅度代替证据，不自动提交审批 |
| 内部审批驳回 | 记录原因，诉求回到草稿处理或 `needs_info` | **不创建外部请求或工单，不给消费者发回复**；客服修改后以新版本重新送审 |
| 需要正式告知“售后申请被拒绝” | 客服制作 action 为 `reject` 的工单草稿，审批人批准后创建工单 | 这是对外业务决定，有唯一工单和唯一最终回复；与内部审批驳回完全不同 |
| 批准后被修改、审批过期、订单/政策/权限变化 | 旧审批保留为审计历史但标为失效；执行被阻止 | 页面说明失效原因，要求回到新版本重新审批，不“继续执行旧方案” |
| 双击创建、Worker 并发或网络重试 | 使用同一业务操作键；同请求竞争也不能产生第二张工单 | 最终只有一个工单、一条回复和可关联的多次尝试记录 |
| 等待审批时 API/Worker 重启 | 从 DTC 持久记录恢复待审批状态 | 审批人仍可查看原版本，不能退回无人知道的内存状态 |
| 外部已建单但响应丢失或超时 | 进入对账，按 ID 或幂等键查询；确认前不盲目重发 | 显示“结果确认中”，不显示失败后就鼓励重新创建 |
| 按幂等键查询暂无可见记录 | 这不等于权威证明“永远没有建单”；保持对账，经过有限退避后重验，并只用原操作键、原业务参数恢复 | 原请求若迟到，原子幂等和 `(market, request_id)` 唯一约束仍只选出一张工单；绝不换键或改参数重发 |
| E-pig 不可用或限流 | 只读查询有限退避重试；写入区分明确未执行与结果未知 | 显示陈旧数据时间和恢复入口，不伪造订单、工单或成功回执 |
| 游标推进前崩溃或一页重复返回 | 从已提交游标重读，按诉求标识去重 | 可以暂时看到重复拦截记录，但不能丢诉求或重复建处理任务 |
| 消费者试图追加回复 | v1 不提供入口，服务端也不接受追加最终回复 | 页面保留原回复和工单进度，提示既有线下服务渠道（如业务已配置） |

v1 的 `needs_info` 不是隐形聊天室。需要补资料时，客服按既有线下渠道联系消费者，并在 DTC 记录核验结果；当前产品不承诺消费者能在原页面多轮补聊或追加附件。口头或线下材料也不能被系统冒充成消费者在线发言。

## 6. AI、规则与人的责任边界

| 责任 | AI | 确定性规则/服务 | 人 |
|---|---|---|---|
| 身份与市场 | 不参与判定 | 校验消费者归属、员工角色、服务 token 和市场范围 | 管理员维护授权；使用者不越权 |
| 信息理解 | 汇总描述、订单、物流和附件上下文 | 校验数据类型、必填条件和工具返回 | 客服核对原始材料，识别误导或缺失 |
| 政策与证据 | 检索、引用、解释版本化政策，标出不确定 | 检查版本、适用条件和引用是否存在 | 客服/审批人处理冲突和例外 |
| 草稿 | 生成动作建议、内部摘要和消费者回复草稿 | Schema 校验、业务条件校验、版本固化 | 客服修改并对送审版本负责 |
| 批准 | 永远不能批准 | 检查审批人权限、版本、有效期和状态迁移 | 授权审批人逐一批准或内部驳回 |
| 工单写入 | 无直接写权限 | 只有有效持久批准才执行；负责幂等、重试和回执 | 审批人授权；对账人员处理未知结果 |
| 消费者沟通 | 起草一次回复，不自行发送 | 确保最终回复随唯一工单创建且不可变 | 人审定措辞；线下补资料由客服处理 |

政策聊天中已有的模型能力仍是辅助工具。检索文本、工具返回、消费者描述或附件中的指令都不能覆盖权限、改变审批状态或触发未批准写入。

## 7. 业务状态机与合法迁移

以下状态是产品与审计语义，不是对 OpenAPI 字段的重复定义。线路枚举和序列化以契约为准。所有迁移只能由服务端在授权、条件校验和审计后执行；前端不能直接写入状态。每次迁移至少能回答“谁、何时、因何、从哪到哪、关联哪个版本/操作”。

### 7.1 诉求（request）

`pending` 表示 E-pig 已受理、等待 DTC 处理；`needs_info` 是内部补资料状态；`completed` 只表示唯一工单回执已确认。

| 当前状态 | 允许到达 | 触发与守卫 |
|---|---|---|
| `pending` | `processing`、`needs_info` | DTC 持久接收后开始处理；材料不足则进入补资料 |
| `needs_info` | `processing` | 授权客服登记线下补充和核验结果；不能自动创建工单 |
| `processing` | `needs_info`、`waiting_approval`、`failed` | 证据和草稿通过校验才送审；明确无外部写入的内部失败可记录为 `failed` |
| `waiting_approval` | `executing`、`processing`、`needs_info` | 有效批准后执行；内部驳回或版本失效后返工；缺材料则补资料 |
| `executing` | `completed`、`reconciliation_required`、`failed` | 读回成功才完成；结果未知必须对账；只有契约明确拒绝且未产生外部效果时才可记失败 |
| `reconciliation_required` | `completed`、`executing`、`processing` | 找到回执则完成；按契约经过退避和重验后，只能以原键原参数重试；批准失效则返工 |
| `failed` | `processing` | 授权人员确认失败发生在任何外部效果之前并排除故障后重开；不是对消费者的业务拒绝 |
| `completed` | 无 | v1 终态；不能重开生成第二张工单或第二条最终回复 |

禁止 `pending/processing/needs_info → completed` 的直达，也禁止内部审批驳回直接完成诉求。正式业务拒绝必须走批准后的 `reject` 工单。

### 7.2 草稿（draft）

送审后的草稿版本不可原地改写。每次实质修改都生成新版本，旧版本保留供审计。

| 当前状态 | 允许到达 | 触发与守卫 |
|---|---|---|
| `editing` | `ready_for_approval` | 必填材料、动作、回复和证据校验通过 |
| `ready_for_approval` | `pending_approval`、`editing` | 送审时锁定；未送审前可继续编辑并形成新候选内容 |
| `pending_approval` | `approved`、`rejected`、`invalidated`、`superseded` | 人工决定；关键材料变化则失效；创建替代版本则旧版被取代 |
| `approved` | `executing`、`invalidated`、`superseded` | 执行前重验通过才进入执行；尚未派遣时，关键变化使其失效或被新版取代 |
| `executing` | `consumed`、`approved`、`invalidated`、`superseded` | 找到原工单后消耗；只有按契约可用原键原参数恢复时，才按当前有效性返回批准态或历史失效态 |
| `rejected` | `superseded` | 版本保留驳回原因；只能新建版本返工，不能原地改成已批准 |
| `invalidated`、`superseded` | 无 | 历史终态；后续工作指向一个新草稿版本 |
| `consumed` | 无 | 已与唯一工单关联，不可再次用于创建 |

草稿进入 `executing` 后，外部结果未知时保持该执行上下文直至对账完成；后续修改可以产生新候选版本，但不能覆盖正在核对的旧版本。找到原工单时旧版本正常进入 `consumed`；契约允许同键恢复时，才决定返回到仍可用的 `approved`，或归档为失效/被取代。

### 7.3 审批（approval）

| 当前状态 | 允许到达 | 触发与守卫 |
|---|---|---|
| `pending` | `approved`、`rejected`、`expired`、`invalidated` | 有权限的人作决定；到期或关键上下文变化由系统迁移 |
| `approved` | `executing`、`expired`、`invalidated` | 只有执行前重验通过才进入执行；尚未发出外部请求时，到期或关键变化会使其失效 |
| `executing` | `consumed`、`approved`、`expired`、`invalidated` | 查到真实回执后消耗；只有契约允许原键原参数恢复时，才按当前有效性返回可重试状态或失效状态 |
| `rejected`、`expired`、`invalidated` | 无 | 审批记录不可复活；需要时基于当前草稿新建审批 |
| `consumed` | 无 | 已对应一次成功外部结果，不能再次执行 |

审批绑定诉求、市场/订单、动作、规范化执行内容、消费者回复、草稿版本、附件集合、订单关键状态、政策证据版本、申请人与审批人、有效期。修改其中任何会改变业务后果的内容，都不能沿用旧批准。

**失效不等于删除，也不等于撤销已经发出的请求。** 失效审批仍能审计，但执行器必须拒绝新的派遣。审批进入 `executing` 后，即使等待回执期间到期或材料变化，也要先完成对账：找到原工单就把原审批标为 `consumed`；只有契约允许原键原参数恢复时，才根据当前版本和有效期决定能否返回 `approved` 重试，或转为 `expired/invalidated`。不能用状态改写假装外部效果从未发生。

重新验证不是简单检查“Approved 字样”，而是在真正调用外部写入前重算上述条件；重新送审也不能自动延长旧审批有效期。若返工改变了规范化执行内容，必须建立新草稿、审批和业务操作，不能沿用旧幂等键提交不同参数。

### 7.4 业务操作（operation）

一个操作代表一次受批准的业务写入，重试沿用同一个稳定操作标识和幂等键。操作尝试可以有很多条，业务结果只能有一个。

| 当前状态 | 允许到达 | 触发与守卫 |
|---|---|---|
| `prepared` | `dispatching` | 审批和参数已持久化，Worker 取得有效租约 |
| `dispatching` | `awaiting_receipt`、`retry_wait`、`reconciliation_required`、`failed` | 已发送则等回执；只有契约允许的安全失败才直接重试；超时/未知进对账 |
| `retry_wait` | `dispatching`、`reconciliation_required`、`failed` | 有限退避后使用同键；执行前重验失败则停止，不得换键绕过去重 |
| `awaiting_receipt` | `succeeded`、`reconciliation_required` | 读回并核验才成功；响应丢失或无法判定进对账 |
| `reconciliation_required` | `retry_wait`、`succeeded`、`failed` | 查到原回执则成功；按契约退避和重验后只允许同键同指纹重试；明确拒绝且确认未产生外部效果时才失败 |
| `failed` | `prepared` | 仅在失败明确发生于外部效果之前时，经授权重新准备；历史尝试不可覆盖 |
| `succeeded` | 无 | 绑定唯一工单和回执，迟到 Worker 不能改写 |

本地数据库事务不能撤销已经到达 E-pig 的请求。因此“本地失败”与“外部没有发生”不是同义词。

### 7.5 正式工单（ticket）

在 E-pig 确认创建前，`creating` 只是 DTC 的本地投影，不能向消费者宣称工单已经存在。

| 当前状态 | 允许到达 | 触发与守卫 |
|---|---|---|
| `creating` | `open`、`closed` | 核验正常动作回执后为 `open`；经批准的 `reject` 可直接以业务已拒绝的关闭态出现 |
| `open` | `processing`、`closed` | E-pig 的售后业务进展驱动；DTC 不擅自推进实物履行 |
| `processing` | `closed` | E-pig 确认处理结束 |
| `closed` | 无 | v1 不重开；最终回复仍保持原文 |

工单状态可以变化，**最终消费者回复不随状态追加或改写**。诉求收到任何有效工单回执后，即锁定“一诉求一工单”的 MVP 约束。

### 7.6 对账（reconciliation）

| 当前状态 | 允许到达 | 触发与守卫 |
|---|---|---|
| `required` | `checking` | 未知结果被授权 Worker 或人员领取 |
| `checking` | `matched`、`same_key_retry_eligible`、`manual_review`、`required` | 找到回执；按契约完成退避和重验后允许同键同指纹恢复；信息不足转人工；瞬时查询失败则继续查询 |
| `matched` | 无 | 绑定同一工单，操作成功、诉求完成；对账记录保留 |
| `same_key_retry_eligible` | 无 | 本次对账以“只允许原键原参数恢复”结束，操作进入重试等待；不是建单成功，也不是对外部不存在的证明 |
| `manual_review` | `checking`、`matched`、`same_key_retry_eligible` | 人工登记可核验证据后继续；不能凭猜测选择结果，也不能换键绕过去重 |

`IN_FLIGHT`、瞬时 `not_found`、超时或 5xx 都不是“外部永远不会建单”的证明。恢复安全来自**原键、原业务指纹、原子幂等约束和一诉求一工单唯一约束**：即使原请求迟到，也只能留下一个结果。任何参数变化都需要新的草稿与审批，不能沿用旧操作键。

## 8. 页面功能与交互逻辑

### 8.1 所有页面共同的状态语言

页面不能把网络请求简单表达成“转圈/失败”两种状态。下列状态在各页面有统一含义：

| 状态 | 必须表达的内容 | 操作原则 |
|---|---|---|
| 加载中 | 保留页面结构，说明正在读取什么；AI 生成与建单分别显示进度 | 防止重复提交，但不锁死无关浏览；不能用动画代替文字状态 |
| 空数据 | 区分“确实没有”“筛选后没有”“尚未生成” | 给清除筛选、返回队列或开始处理等合理下一步，不显示假错误 |
| 无权限 | 说明当前角色或市场不可访问，隐藏受限内容 | 提供返回安全页面，不展示重试按钮误导用户，不泄露对象内容 |
| 错误 | 用可理解语言说明失败环节和是否产生外部效果 | 只读失败可重试；写入未知进入对账，不提供盲目“再建一张” |
| 陈旧 | 明示最后成功同步时间，旧数据可识别但不可被当作最新依据 | 提供刷新；提交/批准/执行前强制重新验证 |
| 冲突 | 说明谁或什么发生了变化，如新版草稿、重复键不同内容、状态已迁移 | 保留用户未提交输入，要求查看新版并明确选择，不静默覆盖 |
| 重试中 | 显示有限重试和退避，写入仍沿用原操作标识 | 允许离开页面；后台任务不因浏览器关闭而重复或取消 |
| 成功 | 展示真实诉求/工单标识、最终状态和下一步 | 只有服务端或回执确认后显示；不能仅靠按钮点击显示“已建单” |

所有 toast 都应有可再次查看的状态历史，不能只用短暂颜色提示关键结果。错误详情中的追踪标识可以复制，但不暴露 token、完整 PII 或内部堆栈。

### 8.2 诉求队列（DTC，新建）

**主要任务：让客服知道有哪些诉求、哪些需要自己处理、数据是否新鲜。**

- 顶部提供市场、处理状态、问题类型和时间范围筛选；市场选择器只出现已授权市场。
- 列表呈现诉求标识、订单脱敏摘要、市场、问题类型、当前状态、更新时间和待审批/对账提示。点击行进入完整详情，不要求客服复制订单号到别的工具查询。
- 页面显示“上次成功同步”和轮询状态。同步失败时保留旧列表但标为陈旧；清空缓存后才显示加载骨架，避免每次轮询都闪烁。
- 刷新、翻页和重连不能替代 DTC 数据库游标。服务端游标推进与浏览器分页完全独立，重复行在服务端按诉求标识去重。
- 另一客服已推进状态时，当前操作返回冲突并提示查看最新版本；列表不静默把新状态覆盖回旧状态。
- 空队列说明当前筛选下没有诉求；无市场权限显示授权说明；读取失败可重试；同步恢复后明确显示最新同步时间。

### 8.3 诉求/工单详情（DTC，新建，核心页）

**主要任务：让客服从证据走到可审批的草稿，并在执行后追踪唯一结果。**

页面按业务阅读顺序组织：

1. **诉求与消费者材料**：原始描述、问题类型、私密附件预览、内部补资料记录。内部备注有明显标识，不混入消费者回复。
2. **订单与物流**：来自 E-pig 的服务视图、查询时间和关键状态。查询失败时区分“快照”与“实时数据”，不把旧快照写成当前事实。
3. **政策证据**：条款原文、来源、版本、适用范围和引用位置。无证据或证据冲突时显示人工处理提示，禁用送审。
4. **AI 建议与草稿编辑**：处理动作、内部摘要、消费者最终回复。重新生成或人工修改会形成新草稿版本，并显示将如何影响已有审批。
5. **审批与操作时间线**：送审、批准/驳回、失效原因、执行尝试、回执和对账。对未授权人员只显示允许范围。
6. **结果区**：建单确认后显示工单编号、状态和不可变回复；结果未知时显示“对账中”，不是绿色成功也不是可重复创建的失败。

交互约束：

- “生成草稿”只调用 AI 辅助，不创建工单；“提交审批”只锁定版本并等待人工；“执行”由系统在有效批准后触发，页面没有绕过审批的隐藏捷径。
- 附件预览单独加载。预览失败不阻塞查看其他非敏感信息，但不能把无权限当成“文件不存在”。
- 草稿保存冲突时并排提示当前版本与最新版本，用户确认后再基于新版修改。
- 审批后详情变为只读执行视图；若批准失效，明确列出需重新核对的政策、订单、权限或草稿差异。
- 重试读取、重试 AI、重试建单是三种不同动作。只有第三种具有外部写入风险，必须沿用原操作并遵守对账结果。

### 8.4 审批中心（DTC，新建）

**主要任务：让审批人判断“这一版是否允许形成这一张工单”。**

- 待审批列表按市场、等待时长和动作类型筛选，只显示当前审批人可处理的范围。
- 决策页同时展示消费者诉求、订单关键状态、私密凭证、政策版本和引用、动作及其后果、完整最终回复、草稿版本和有效期；有旧版本时提供差异摘要。
- “批准”和“内部驳回”使用不同文案。内部驳回必须填写面向内部的原因，并明确提示“不会创建工单，也不会通知消费者”。
- 若业务上要正式拒绝消费者，审批人看到的是 action 为 `reject` 的工单方案；批准它会创建带最终回复的工单，不能和内部驳回混用。
- 点击决定后按钮进入提交中，服务端条件更新防止并发重复批准。已处理、已过期或已失效时显示冲突并要求查看最新版本。
- 批准成功表示“已允许系统按此版本执行”，不提前等同于“工单已创建”；页面随后展示执行/回执状态。
- 加载、空待办、无权限、读取失败、版本陈旧、并发冲突、有限重试和成功均使用第 8.1 节状态语言。审批决定不能因重试变成两次有效迁移。

### 8.5 政策问答（DTC，保留现有聊天页并补业务边界）

**主要任务：让内部客服随手查政策，不让聊天页成为绕开工单流程的后门。**

- 继续提供现有内部政策检索和问答；回答展示引用、政策版本和知识更新时间。
- 支持把引用或建议手动带回详情草稿的计划入口，但这只是复制辅助内容，不自动送审或执行。
- 消费者订单查询、附件读取和工单写入不在此聊天页开放。内部政策聊天也不等于消费者售后多轮聊天。
- 无结果时明确说“未找到足够依据”，提供调整关键词或去详情人工处理；不生成貌似确定的政策。
- 政策更新后标为陈旧并要求重新检索；来源相互冲突时并列展示并建议人工判断。
- 加载/流式生成、空结果、无权限、模型或检索失败、陈旧、证据冲突、重试和带引用成功均有文字状态。重试问答不会触发任何业务写入。

### 8.6 E-pig 订单详情页（消费者端，计划扩展）

**主要任务：让消费者从本人订单提交一次诉求，并能回来查看进度和最终答复。**

- 无有效订单归属凭据或订单不属于当前浏览器会话时，沿用 E-pig 会话与无权限流程；页面不显示内部员工、审批或操作信息。
- 无售后诉求时显示申请入口和清楚的条件说明；已有诉求时优先显示当前进度，避免用户重复申请。
- 申请表提供问题类型、描述和附件选择。每个文件即时校验数量、格式和大小，提交中防止双击；失败重试沿用原幂等上下文。
- 上传成功只表示私密材料已被 E-pig 接收，不表示 AI 已认可证据。提交成功后显示诉求已受理，不虚构 AI 对话。
- 进度区只展示 E-pig 真实持有的状态：诉求已受理后显示“售后处理中”，工单创建后显示工单编号、当前业务状态和唯一最终回复。DTC 的 `needs_info`、待审批和对账状态在 v1 不同步到消费者端；客服需要补资料时通过既有渠道联系，页面不显示不存在的在线补聊输入框。
- 工单回复不可编辑、追加或再次建单。消费者是否能看到工单只由 E-pig 的真实记录决定，不等待 DTC 推送内部状态。
- 页面加载失败可重试；已有缓存必须标陈旧及更新时间；重复提交冲突时恢复原诉求；附件拒绝指出具体原因；无权限不泄露任何订单/工单内容；成功只来自 E-pig 真实记录。

## 9. 附件与唯一消费者回复

### 9.1 私密附件规则

- 每个诉求最多 **3 个**附件；每个文件最大 **5 MiB**；仅允许 **JPEG、PNG、WebP**。
- 上传时必须指定目标订单，E-pig 校验该订单归属并把附件绑定到稳定消费者主体和订单；诉求只能引用同一主体、同一订单的附件，跨订单或跨主体引用一律拒绝。
- E-pig 在服务端同时检查数量、大小、声明类型与实际文件内容，不能只信扩展名或浏览器 MIME。非法文件明确拒绝，不静默压缩成另一种格式或丢弃。
- 文件存入 E-pig 私密存储。消费者本人、具备对应角色/市场的客服与审批人，以及执行必要服务视图的后端，才能通过授权内容读取；不使用永久公开 URL。
- 已提交附件集合参与草稿和审批版本。替换、增加或删除附件会使相关批准失效；v1 没有消费者在线追加附件的多轮流程。
- 预览失败、病毒/内容安全扫描失败或授权撤销都应阻止不安全展示，并给出可理解的状态。日志、分析事件和错误报告不记录文件字节、公开链接或完整客户资料。

### 9.2 一次、不可变的最终回复

最终回复是工单创建时由 E-pig 持久保存、面向消费者的正式业务结论。它必须来自被批准的同版草稿，与工单动作一致，并在创建后不可编辑、追加或删除。

这条规则带来四个直接结果：

1. 内部审批驳回只是返工，没有工单，也没有最终回复。
2. 正式业务拒绝必须提交并批准 action 为 `reject` 的草稿，创建工单后向消费者展示拒绝结论。
3. 重复建单返回原工单和原回复，不能利用重试改写措辞。
4. 回执未知时，客服在 DTC 看到“结果确认中”；消费者只看到 E-pig 已真实保存的进度。若 E-pig 已建单，消费者可以按该记录看到工单，DTC 则在核验回执后才更新自己的成功状态。

后续若需要多轮消费者沟通，必须另立产品版本、状态机、权限与兼容设计，不能在 v1 通过“再写一条回复”悄悄扩展。

## 10. 非功能产品要求

### 10.1 隐私与安全

- 全链路最小化 PII：列表默认脱敏，详情只展示处理所需信息；传输使用受保护通道，存储加密和密钥管理沿用部署平台能力。
- 消费者响应采用独立序列化白名单，审批字段、内部版本、完整地址和附件存储地址即使被加入通用领域对象也不得输出。接收方忽略未知字段的兼容策略，不能成为生产方泄露敏感字段的许可；安全相关响应的新增字段必须经过契约评审。
- Bearer token、员工会话、消费者凭据、私密附件地址不得进入前端日志、分析事件或错误堆栈。日志使用内部关联标识，不记录完整订单地址和附件内容。
- 权限撤销立即影响新读取和新执行；已缓存内容按最短必要时间失效。授权读取附件也可审计。
- 数据保留、删除和法律保全按目标市场政策配置；实施前须明确期限和责任方，不以“永久保留所有原始数据”为默认值。

### 10.2 审计与可观测性

审计记录采用追加式历史，至少覆盖身份/市场校验结果、诉求接收、附件集合变化、草稿版本、送审、批准/内部驳回、失效、每次外部尝试、回执、最终回复版本、状态迁移和人工对账依据。审计界面能按诉求串起完整故事，而不是只有一条“成功”。

运行监控以 `trace_id`、诉求、操作和工单等内部标识关联 DTC 与 E-pig，但不把敏感内容放入标签。计划监控：

- 各市场轮询延迟、游标停滞、重复去重和队列等待时长；
- 订单/物流读取成功率、附件授权拒绝、AI 生成时长与无证据比例；
- 待审批时长、审批失效原因、未审批写入拦截；
- 建单重复拦截、冲突、超时、未知结果、对账积压和恢复耗时；
- 消费者提交失败、页面错误、可访问性和本地化缺失。

告警阈值在 M5/M6 依据实测基线设定，不能在未测量时宣称已有 SLA。

### 10.3 可访问性与本地化

- 新页面以 WCAG 2.1 AA 为设计和验收目标：完整键盘操作、可见焦点、表单标签、错误关联、合理标题层级和足够对比度。
- 状态不只靠颜色；加载和流式更新以不打扰的方式向辅助技术播报；审批、冲突和对账等关键结果必须可被重新读取。
- 表格和差异视图在小屏有可读替代，不要求用户只能靠横向滚动比较批准内容。
- DTC 内部界面首期可用简体中文，但市场、时间、货币和政策原文不能硬编码为单一地区。消费者端沿用 E-pig 的市场/locale 机制。
- 时间同时保留可核验的绝对时间，按用户时区展示；金额沿用订单币种，不做隐式换算。AI 翻译的消费者回复仍须人工审定，政策翻译不能替代原版本依据。

### 10.4 性能与可用性预期

以下是**计划验收预算，不是当前实测结果**，适用于约定测试负载、正常网络和依赖健康时：

| 体验 | 初始目标 | 降级要求 |
|---|---|---|
| 已缓存队列和普通详情交互 | p95 在 2 秒内可用 | 超过预算显示明确加载状态，不阻塞键盘操作 |
| 依赖 E-pig 实时的订单/物流读取 | p95 在 5 秒内返回或分类失败 | 可展示带时间的旧快照，但批准/执行前必须重验 |
| 消费者非附件提交与进度读取 | p95 在 3 秒内返回确定受理/失败 | 上传时长单独统计；超时不能误报已受理 |
| AI 草稿 | 异步展示进度，p95 目标 60 秒内形成结果或可操作失败 | 客服可查看已有材料；AI 慢不阻塞人工编辑 |
| 健康依赖下的新诉求可见性 | 轮询与处理合计目标 60 秒内 | 显示最后同步时间，游标停滞可告警 |
| 建单与回执 | 不设置虚假固定成功时间；区分外部处理和对账等待 | 超时进入结果确认中，后台恢复，不强迫用户停留 |

M5 用固定场景测量并校正预算，M6 小范围试用再确认是否满足实际工作节奏。性能目标不能通过跳过重验、审批或回执核验来达成。

## 14. 术语表

| 术语 | 白话解释 |
|---|---|
| DTC / 售后中台 | 本仓库计划的内部客服与审批系统，是人工审批权威，不拥有消费者订单主数据。 |
| E-pig | 独立电商前台，拥有消费者、订单、诉求、附件、正式工单和消费者回复。 |
| 市场（market） | 订单所属业务区域，也是权限隔离边界；不是仅用于界面显示的标签。 |
| 诉求（request） | 消费者提出的售后问题，是处理输入，不等于已批准工单。 |
| 工单（ticket） | 经人工批准后由 E-pig 创建的正式售后业务记录。 |
| 草稿版本 | 某一时刻锁定的动作、依据和回复内容；修改会产生新版本。 |
| 持久人工审批 | 保存在数据库中、由有权限的人作出的决定，重启不会丢，AI 不能代替。 |
| 内部审批驳回 | 审批人要求返工；没有外部工单和消费者回复。 |
| 业务拒绝（`reject`） | 经批准的正式工单动作，用唯一最终回复告知消费者申请被拒绝。 |
| 幂等 | 同一件事重复提交仍只产生一个业务结果；同键不同内容必须冲突，不能覆盖旧结果。 |
| 稳定游标 | 服务端记住“可靠处理到哪里”的位置；它不是浏览器页码，持久推进前要先保存数据。 |
| 回执 | E-pig 对工单创建结果的可查询证明；本地按钮成功不等于收到回执。 |
| 陈旧数据 | 曾经读取成功、但可能已不是最新状态的数据，必须显示同步时间并在关键动作前重验。 |
| 冲突 | 当前操作基于的版本或参数已被其他变化取代，需要查看最新版本，不能静默覆盖。 |
| 对账 | 外部结果不确定时，通过 ID/幂等键查询和人工证据查明“究竟有没有建单”的过程。 |
| 最终回复 | 随唯一工单创建、向消费者展示且 v1 不可修改或追加的一次正式答复。 |
| 操作账本 | DTC 对每次外部写入意图、尝试、回执和恢复的追加式记录。 |

## 15. 产品决策日志

| 日期 | 决策 | 理由与影响 |
|---|---|---|
| 2026-11-04 | DTC 是唯一审批权威；E-pig 只保存工单上的审批/草稿版本审计字段，不做新审批系统或 JWS。 | 避免两套批准状态互相矛盾；审批仍由 DTC 持久化，E-pig 负责业务写入和归属校验。 |
| 2026-11-04 | 复用 E-pig 既有签名购物车会话与订单归属凭据，不新建消费者账号或强制登录。 | 减少身份分裂；订单归属仍由 E-pig 服务端判断。 |
| 2026-11-04 | 服务间采用 Bearer token + 允许市场配置，员工另按角色/市场授权。 | 服务身份、消费者身份和员工身份各负其责，任何一层都不能替代另一层。 |
| 2026-11-04 | 所有工单写入均需持久人工批准，包括业务 `reject`；没有低风险自动写入例外。 | 保持单一、可审计的安全边界，避免模型自行决定何时可绕过人工。 |
| 2026-11-04 | DTC 采用轮询稳定诉求 feed 和持久游标，E-pig 用连续已提交高水位避免并发提交漏数；v1 不做 webhook，游标与重放不过期。 | 减少外部回调鉴权面；以重复可读和去重换实现简单、恢复可靠。未来裁剪 feed 前必须先设计版本化重同步。 |
| 2026-11-04 | 附件固定为最多 3 个 JPEG/PNG/WebP、每个 5 MiB，E-pig 私密存储并授权读取内容。 | 给消费者明确预期，同时限制带宽、恶意内容和隐私暴露面。 |
| 2026-11-04 | 一个诉求在 v1 只形成一张工单和一条不可变最终回复，不做消费者多轮聊天或追加回复。 | 保证审批内容与消费者看到的内容一致，避免回复版本脱离批准版本。 |
| 2026-11-04 | 缺资料/证据不足进入 `needs_info`，由客服线下跟进；不伪装自动多轮追问，不建临时工单。 | 在现有能力范围内诚实呈现流程，避免 AI 编造证据或消费者消息。 |
| 2026-11-04 | 内部审批驳回不产生外部请求/工单；正式业务拒绝以经批准的 `reject` 工单和最终回复表达。 | 区分“方案需要返工”和“对消费者的正式决定”，避免误发消息。 |
| 2026-11-04 | 外部写入超时先查回执并对账；查不到或 `IN_FLIGHT` 都不是不存在证明，只允许按契约用原键原业务指纹恢复。 | 本地超时不能证明外部未成功；原子幂等与一诉求一工单约束同时兜住迟到请求，防止换键制造重复工单。 |
| 2026-11-04 | E-pig 在创建事务中同时校验当前订单版本、业务条件及 `(market, request_id)` 唯一约束，并保存工单、回复、回执和状态迁移。 | 关闭不同幂等键竞争和审批后订单变化造成的重复/陈旧写入；这不把 DTC 审批权转给 E-pig。 |
| 2026-11-04 | 缺订单号或空描述在消费者入口拒绝；`needs_info` 只用于已受理但证据不足的诉求。 | 必填格式错误不应制造无效队列数据，已受理后的业务补资料才有内部跟进状态。 |
| 2026-11-04 | 契约包版本使用 SemVer，线上版本头只表达主版本兼容；消费者安全响应用生产白名单，幂等重放返回原对象当前视图。 | 支持兼容 minor 升级，避免响应泄露和旧快照覆盖新状态；具体规则由 OpenAPI 与对接规范固定。 |
| 2026-11-04 | MVP 不做真实退款、自动取消订单、webhook 或全自动 AI 客服。 | 将首期收敛到可审核、可恢复、可验证的工单闭环；工单动作不等于实物或资金履行。 |
