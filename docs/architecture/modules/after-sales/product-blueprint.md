# 产品形态与用户旅程：AI 辅助的售后客服工作台

更新日期：2026-11-04。状态：产品方向已确认，页面与流程均为计划，尚未实现。

## 这份文档回答什么

当前仓库能看到的是一个问答演示页，容易让人误以为"这个产品只是一个 AI 问答平台"。本文说明最终产品是什么、谁在哪一步做什么、哪些页面要新建。上游问答页是能力演示，不是产品终态；我们复用的是检索、路由、工具调用与护栏这些内核。

一句话定义：**面向企业内部客服与审批人的售后工作台，AI 负责查资料和写草稿，规则负责权限和业务条件，人负责决定。** 消费者入口由独立电商前台 E-pig 承担，对接方式见 [E-pig 售后对接契约](epig-contract.md)。

## 两个端与一条完整故事线

场景：消费者在 E-pig 买了一张餐桌，收货发现桌角破损。

| 步骤 | 谁在哪里操作 | 看到 / 发生什么 |
|---|---|---|
| 1 | 消费者，E-pig 订单详情页 | 点"申请售后"，选"商品破损"，填描述、传照片，提交 |
| 2 | E-pig 系统 | 生成诉求单（工单的雏形），状态"待处理" |
| 3 | 客服，Agent 工作台"诉求队列" | 看到新诉求，点开进入工单详情页 |
| 4 | 工单详情页，AI 自动准备 | ① 订单与物流信息（经 Connector 从 E-pig 查询）② 适用政策原文与出处，如"大件家具签收 48 小时内破损可退换" ③ 处理建议与给消费者的回复草稿 |
| 5 | 客服 | 核对资料，修改草稿，选择处理方案（补发 / 退货） |
| 6 | 审批人（仅退款等高风险动作） | 看到方案、金额、政策依据与草稿版本，批准或驳回 |
| 7 | 系统 | 创建正式售后工单，回执同步到 E-pig；重复点击不产生第二张工单 |
| 8 | 消费者，E-pig 订单页 | 看到"售后处理中：已安排补发"与客服回复 |

AI 在这里的角色是客服的"资料员 + 文书"，不是代替客服聊天或做决定。第 4 步的检索与草稿复用当前已有内核；第 5～7 步的规则校验、持久审批与幂等创建是主要新建工作。

## 工作台页面地图（计划）

```text
Agent 工作台（本仓库 frontend/ 改造）
├─ 诉求队列（新建）        待处理 / 处理中 / 待审批 / 已完成
├─ 工单详情页（新建，核心） 订单信息 + 政策依据 + AI 草稿 + 操作按钮
├─ 审批中心（新建）        高风险动作批准 / 驳回，绑定草稿版本
└─ 政策问答（现有聊天页保留）客服随手查政策的辅助工具
```

E-pig 侧只需要售后业务域：诉求与工单数据、对应 API、订单详情页的售后入口和进度展示。不另建独立售后平台，不在 E-pig 内嵌客服处理后台。

## 在线客服的三种形态与开放顺序

| 形态 | 消费者能做什么 | 开放前提 | 计划阶段 |
|---|---|---|---|
| A. 售后工单入口 | 提交诉求（订单 + 问题类型 + 描述 + 图片），查看进度与回复 | E-pig 登录态与订单归属校验 | 首期，随 M3 |
| B. 政策问答聊天窗 | 问退货、配送、安装等政策，只读检索，不查订单、无写权限 | Agent 提供消费者只读通道与限流 | 首期后可加 |
| C. 全自动 AI 客服 | 查"我的订单"、发起退货，必要时转人工 | 服务端身份、订单归属、消费者工具白名单、严格护栏与人工接管 | Phase 2，依赖 M2 完成 |

当前 `user_id` 来自请求体、未经认证，形态 C 在此问题解决前不开放；这也与 README 的"使用边界"一致。

## 与里程碑的关系

- M2：可信身份、店铺（E-pig 市场）权限、Connector、事务与迁移——形态 C 的安全前提也在此打牢。
- M3：打通故事线 1～8 步，是产品闭环的验收主线。
- M4：重复提交、重启恢复、超时回执对账在真实链路上演练。
- 总体背景仍见 [项目方案](../../../project-plan.md)；本蓝图不扩大首期范围，真实退款、自动取消订单仍不在首期。
