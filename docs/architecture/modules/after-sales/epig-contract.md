# E-pig 售后对接契约与防偏移规范

更新日期：2026-11-06。状态：v1产品与契约规则已确认；E-pig运行时、DTC Connector与执行核心已有阶段验收，跨仓旅程和页面仍单独验收。本文维护可靠性语义，实际进度与证据见[产品蓝图](product-blueprint.md)和[流程实施记录](../../../records/after-sales/dtc-workflow.md)，不能由契约存在推定运行时或联调通过。

## 1. 这份规范约束什么

两个仓库并行开发时，最危险的不是少一个字段，而是各自认为“对方会这样处理”：一边重复建单，另一边却靠重试再建一张；一边认为审批已核验，另一边只收到一个无法验证的版本号。

本规范用四层约束消除这种偏移：

1. [产品蓝图](product-blueprint.md)固定“应该发生什么”。
2. [OpenAPI v1](../../../../contracts/epig-after-sales/v1/openapi.json)固定 HTTP 路径、字段、类型、状态码、请求头和错误结构。
3. [共享符合性样例](../../../../contracts/epig-after-sales/v1/fixtures/manifest.json)让两个仓库执行同一批正反例。
4. 版本锁、变更流程和自动检查阻止单方面修改契约。

Issue 只记录决定、进度和证据，不是另一份接口定义。E-pig 的 `docs/engineering/after-sales-agent-integration.md` 只描述其内部实现，也不能覆盖本契约。

## 2. 系统与数据边界

E-pig 是独立的 Next.js 多市场电商前台（`au/sg/us`），本系统是售后中台：客服工作台、政策检索、审批与工单执行协调。

```text
消费者 → E-pig（订单/诉求/正式工单） ←HTTP→ 售后中台 ← 客服 / 审批人
```

- 两边通过 HTTP API 协作，**不共享数据库**。
- E-pig 持有订单、消费者诉求、附件和正式工单；中台持有订单快照、政策证据、AI 草稿、审批、任务、操作账本和对账状态。
- E-pig 不建立客服审批后台；中台不另建消费者商城或直接向消费者推送消息。
- 首期不做消费者 AI 自动回复、真实退款、自动取消订单、webhook 或多轮消费者聊天。

## 3. 身份与信任边界

### 消费者请求

E-pig 复用现有签名购物车 Cookie 验证消费者是否能访问目标订单，不要求为本需求另建账号系统。E-pig 必须验证签名、有效期和精确市场匹配，从已验证的 `cart_id` 得到稳定主体，再检查订单、诉求、工单和附件与该主体的持久关联。Cookie 合法本身不证明同市场的任意订单都属于该消费者。

浏览器提交的 `user_id`、订单号、附件 ID 或原始 Cookie 文本都不是授权依据。消费者幂等作用域使用稳定 `cart_id`，Cookie 续期或重新签发不能改变重试身份。消费者越权访问统一按 `not_found` 语义处理，避免泄露“这个订单属于别人”。附件上传、诉求读取、工单读取和附件内容下载都要分别校验归属，不能因为知道一个 ID 就绕过检查。

### 中台服务请求

- 服务间使用 `Authorization: Bearer`，密钥只存在服务端环境变量，不下发浏览器，不写入日志。
- E-pig 将服务凭证绑定允许访问的市场列表，并校验路径市场；配置未授权的市场必须拒绝。
- DTC 另外校验客服或审批人的角色、市场成员关系和订单范围。服务 token 能访问某市场，不代表当前客服也有权访问。
- 服务接口使用独立的 service API 视图，不改变 E-pig 现有消费者订单 API 的响应兼容性或脱敏边界。

## 4. 审批权威与执行责任

**所有正式工单创建都必须先完成 DTC 持久化人工审批。** 高风险的退款在 v1 同样只创建售后工单，不触发真实支付退款。

DTC 是审批权威，必须在调用 E-pig 前重新检查：

1. 当前执行人、审批人、市场与角色仍有效。
2. 审批处于有效状态，未拒绝、过期、撤销或被新草稿取代。
3. 工具、动作、诉求、订单和规范化参数与审批对象一致。
4. 草稿、政策和关键订单版本未变化；发生变化时重新检查或审批。
5. 业务规则和诉求状态仍允许创建工单。

请求中的 `approval_id`、`draft_version`、`policy_version` 和 `order_version` 是审计与核对字段。**E-pig 不凭这些字段独立判断 DTC 审批是否有效，也不另建一套审批系统。** 它必须验证服务身份、市场、诉求状态、业务约束和幂等记录，并保存实际收到的版本与回执。

其中 `order_version` 同时是 E-pig 自身订单状态的并发守卫：E-pig 必须在创建事务中把它与当前订单版本比较，不一致返回 `ORDER_VERSION_CONFLICT`。这防止 DTC 重验后到 E-pig 提交前发生的订单变化，不代表 E-pig 接管 DTC 的审批或政策判断。

审批驳回是 DTC 内部返工，不调用工单 API；最终业务拒绝则由有权限的人批准 `reject` 动作和最终回复后形成正式结果，两者不能混用。

## 5. 诉求同步与队列语义

v1 只采用 DTC 轮询，不开放外部 webhook 回调面。

- E-pig 提供按市场内唯一、单调递增 `sequence` 排序的追加式诉求 feed；新诉求进入 feed 后，后续状态变化不会把它从历史序列中删除。
- 单调分配序号不等于提交可见顺序。E-pig 必须维护连续、已提交的发布高水位：只有所有前序记录都已可见时才推进，任何记录都不得在已发放游标的位置或之前新出现，从机制上避免“43 先可见、42 后提交”造成永久漏读。v1 采用按市场串行的发布计数器，计数器递增、诉求发布记录和其他业务写入在同一数据库事务完成；事务回滚同时回滚序号分配，不能直接使用回滚后留下永久空洞的数据库 sequence。
- 游标表示“最后一条已持久处理的序列”，不是内存页码，也不使用会随状态变化而漏数据的 `status=pending` 偏移分页。
- 每个非空页都返回非空 `next_cursor`，包括当前末页；`has_more` 只表示响应时是否还有已发布记录。空页返回当前位置，调用方不能自行猜测或构造游标。
- v1 游标和 feed 重放不过期。任何保留期裁剪都必须先提供版本化的无遗漏重同步契约，不能直接删除历史后让旧游标失效。
- DTC 在同一数据库事务内保存诉求、去重记录和新游标。处理失败时不推进游标；重复拉取由诉求 ID 和序列去重。
- 工作台的“待处理 / 处理中 / 待审批 / 已完成”是 DTC 的处理视图，不要求 E-pig 复制这些内部状态。
- 轮询暂停或 E-pig 暂时不可用时，队列展示数据陈旧状态，不把最后一次成功拉取的数据伪装成实时结果。

## 6. 幂等、并发与回执

幂等是“同一个业务操作重复提交仍得到同一个结果”，不是简单的本地响应缓存。

- 消费者创建诉求、DTC 创建工单都使用 `Idempotency-Key`。
- 键按市场、已认证主体和操作类型限定作用域；不同操作或不同主体不能互相读取结果。
- 同键同参数指纹返回**原业务对象的当前表示**，并标记为幂等重放；不能返回创建时的旧快照，也不能用旧快照覆盖调用方更新后的状态。同键不同参数返回冲突，不能复用旧结果。
- 参数指纹基于规范化业务参数。工单指纹包含诉求、动作、回复和版本字段，不因请求 ID、重试次数等传输信息变化。消费者诉求指纹中的附件列表缺失时等同空数组，附件 ID 在指纹计算前排序；数组原始顺序不改变同一诉求的幂等身份。
- 数据库唯一约束选出一个创建者；并发请求等待或读取同一结果，不能先生成两张工单再靠查询去重。
- 除幂等键外，E-pig 还以 `(market, request_id)` 建立原子唯一约束。创建工单、保存不可变回复和回执、写入幂等结果及诉求 `pending → ticket_created` 必须在同一数据库事务完成。不同操作键竞争同一诉求时，相同业务指纹得到原工单当前视图，不同指纹得到 `REQUEST_STATE_CONFLICT`。
- 幂等记录与对应业务对象同生命周期保留。具体归档方式不得改变按原键恢复原结果的能力。

E-pig 提供按工单 ID 和按幂等键查询回执的接口。已完成返回原工单当前表示；仍在提交或无法判定返回 `202 IN_FLIGHT`；`404` 只表示当前没有可见记录，**不是原请求永远不会提交或外部永远不存在的证明**。网络错误、超时或 5xx 同样属于结果未知。

恢复安全来自原键、原业务指纹、原子幂等约束和 `(market, request_id)` 唯一约束。即使原请求迟到，也只能留下一个业务结果。错误中的 `retryable` 只表示当前 HTTP 请求能否立即按原样重试；创建工单的 `5xx` 即使可恢复，也必须标为 `LOOKUP_FIRST`，不能把这个字段理解成允许盲目再建一次。

## 7. 超时、重试与恢复

| 情况 | DTC 必须执行 | 禁止行为 |
|---|---|---|
| 只读查询超时、连接错误或限流 | 使用有次数和时间上限的退避重试，并尊重限流信息 | 无限重试或把旧数据说成实时 |
| 创建工单前已确认请求未发出 | 使用同一业务幂等键执行 | 为每次尝试生成新键 |
| 创建请求超时或连接丢失 | 先按原幂等键查询回执；查到后保存同一结果，`IN_FLIGHT` 时有限退避再查 | 未查询就盲目重发，或把一次 `404` 当成永久不存在 |
| 查询暂无可见记录 | 保持对账，经过有限退避并重新验证后，只用原键、原业务指纹恢复；迟到请求由原子约束去重 | 换键、修改参数后复用旧审批，或宣称已证明外部未执行 |
| 回执查询持续失败或结果矛盾 | 进入 `reconciliation_required`，等待自动恢复或人工对账 | 伪造成功、伪造未执行或换键再写 |
| 外部已创建、本地保存前崩溃 | 恢复时先查操作账本和回执，再补本地结果 | 仅根据任务“未完成”重新创建 |

恢复时，“任务执行到哪一步”和“外部是否已经产生效果”是两个问题。Graph 检查点回答前者，操作账本和 E-pig 回执回答后者。

## 8. 附件与回复边界

- 附件由 E-pig 私有存储，物理存储由 adapter 内部决定；不使用永久公开 URL，不在数据库或 JSON 中传 base64 文件内容。
- v1 最多 3 个 JPEG/PNG/WebP 文件，每个不超过 5 MiB。E-pig 校验真实文件类型、大小和归属；中台展示前通过授权内容接口读取。
- 上传成功不等于诉求已提交；上传必须绑定目标订单和稳定消费者主体，诉求只引用同一消费者、同一订单上下文中的附件 ID，跨订单引用必须拒绝。
- 消费者与 DTC 使用各自的附件内容路由和鉴权声明，不让 service middleware 猜测消费者路径上的 Bearer token；两边都执行对象级归属/市场检查。
- v1 在创建工单时写入一条不可变最终消费者回复，没有后续追加回复 API。
- 日志不记录 token、附件内容、完整客户描述或完整回复；通过 `request_id`、诉求 ID、任务 ID 和操作 ID 关联排障。

## 9. 错误与线上兼容规则

具体字段、状态码和错误码只以 OpenAPI 为准，本文不另维护一份清单。两个仓库共同遵守：

- 请求出现未知字段时拒绝，避免双方对拼写错误产生不同解释；接收方可以忽略服务响应中的未知可选字段，但消费者、错误、脱敏收件人和 service 订单等安全相关 DTO 的生产方必须使用字段白名单并拒绝额外属性，不能复用通用序列化器输出审批字段、完整地址、存储 URL 或任意诊断对象。其他服务响应的 additive 兼容策略不能扩展到这些安全 DTO。
- 金额使用整数最小货币单位和 ISO-4217 币种；时间使用 UTC RFC3339；ID 是不透明字符串，不依赖其格式或自增规律。
- 错误响应包含稳定机器码、安全的人读信息、请求关联 ID、是否可立即重试和恢复动作；内部堆栈、SQL、token 和客户资料不能进入响应。
- 契约包使用 `1.0.0` 这样的 SemVer 并由 source lock 固定；线上版本头只表达主版本兼容，v1 的值为 `1`。主版本不兼容时快速失败，不能在猜测的字段语义下继续写入。

## 10. 版本锁与 E-pig 强制接入

DTC 的 `contracts/epig-after-sales/v1/` 是源契约包，包内 `SHA256SUMS` 固定 OpenAPI 和全部样例的字节内容。只有语义检查全部通过后，维护者才能显式运行 `python scripts/check_epig_after_sales_contract.py --write-checksums` 更新它；普通测试只读校验，不能自动改写。

E-pig 必须将完整目录原样 vendor 到自己仓库，并增加 `source-lock.json`，至少记录：

- 源仓库、不可变源提交、跟踪源分支和契约版本。
- 每个 vendor 文件的相对路径与 SHA-256。
- 同步时间和关联的两个仓库 Issue/PR。

硬性规则：

1. E-pig 只能修改 lock 所指向的版本，**不能直接编辑 vendor 副本**。
2. 同步是显式命令；测试和构建不得隐式下载或改写契约。
3. 本地检查逐文件比较 SHA-256；另一个检查比较跟踪源，发现源已前进时报告陈旧。
4. Zod、TypeScript 类型和 E-pig adapter 都是契约的消费者，不是新的字段正本。
5. 两个仓库必须原样执行共享正反 fixtures；不能用“自己的测试已通过”替代共享符合性。
6. E-pig 将 digest、fixture 和生成物新鲜度检查纳入 `pnpm verify`；DTC 将源契约检查纳入 CI。

当前只存在源契约与本规范。E-pig vendor、运行时符合性、跨仓 freshness 和 `pnpm verify` 门禁以 E-pig#2 的实际完成证据为准。

## 11. 变更流程：任何一边都不能单独改契约

契约版本从 `1.0.0` 开始：

- **Patch**：不改变行为的说明、例子或错误描述澄清。
- **Minor**：向后兼容的新增，例如可选请求能力或响应可选字段；E-pig 先支持，DTC 再使用。
- **Major**：删除/改名字段、修改必填性或枚举含义、改变路径、鉴权、状态、幂等或回执语义；新建主版本目录并保留迁移期。

每次变化必须按同一顺序完成：

1. 在 DTC#2 提出变化、原因、兼容性和受影响需求/验收 ID。
2. 修改产品语义、OpenAPI、共享 fixtures 和验证记录；运行源契约检查。
3. 两个仓库分别建立关联变更，E-pig 更新源提交和 digest，完成运行时符合性。
4. 联调通过后同步 DTC#1/#2 与 E-pig#2；未完成的一边保持明确待办，不能宣称整体完成。

开发 PR 或任务评论必须包含：`contract_version`、不可变源提交、契约 digest、共享 fixture 结果、实现测试、文档更新和未验证范围。禁止先合并一边的行为变化，再让对方“适配现状”。

`.github/CODEOWNERS` 用于路由产品和契约审查；只有仓库分支保护将相应检查设为必需后，才形成 GitHub 合并硬门禁。

## 12. 两边实现责任与验收

E-pig#2 负责本仓 contracts、adapter、Route Handlers、附件存储、订单页组件、权限/幂等测试和契约 vendor；DTC#2 负责跨仓联调与整体验收。

本仓库后续实现 `EpigConnector`、持久诉求游标、工单状态机、审批/操作账本和工作台页面，Fake 与 E-pig 通过同一 Connector 接口切换。

必须共同通过产品蓝图中的验收场景，尤其是重复提交、审批等待重启、版本变化、回执丢失恢复、游标无遗漏、跨市场访问、附件越权和 E-pig 不可用降级。结构校验通过不等于这些业务场景已实现或已联调。
