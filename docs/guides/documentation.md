# 文档设计与维护规范

更新日期：2026-11-03。状态：本 fork 的文档维护约定。

本规范从 Hextech 的目录职责、稳定主题、技术设计与证据原则适配，并保留本项目上游教程连接源码与解释取舍的长处。它是人读正本；[文档技能](../../.agents/skills/dtc-documentation/SKILL.md) 负责提醒助手执行，具体选型见 [技能指南](skills.md)。

## 先让读者知道要解决什么

读者具备前端经验，但未必了解 Python、SQL、模型检索和运维。开头回答：谁遇到什么问题、本文能帮助他完成什么、当前讲的是已有实现还是目标方案。

例如：“客服批准创建工单后服务重启，原来的批准不能丢。我们计划把批准内容存到数据库，再决定从哪一步继续。”之后再解释持久化、检查点和恢复。每个新概念给一句中文解释和本项目例子；类比前端时说明差异。

Markdown 为主要载体，便于代码审查、博客整理和版本追踪。流程复杂时可以用 Mermaid，但必须给出等价文字说明。正文不能依赖截图编号、颜色或读者访问另一张图片才成立。新增 HTML 展示页需要明确用途，不同时维护一份同内容的 HTML 正本。

## 各类内容放在哪里

| 内容 | 权威位置 | 回答的问题 |
|---|---|---|
| 项目背景、范围与整体路线 | [项目方案](../project-plan.md) | 做什么、为什么、有哪些边界 |
| 独立模块的技术设计 | `docs/architecture/modules/<topic>/`，确有独立模块时再建 | 责任、输入输出、数据、失败处理和取舍 |
| 使用/开发/运维指南 | `docs/guides/<topic>.md` | 如何完成一件具体操作 |
| 学习入口与练习 | [学习路线](../learning/README.md)，独立课题才新增文章 | 从业务例子理解概念与代码 |
| 实施、审查与验证记录 | `docs/records/<topic>/` | 哪个版本实际做过什么、还有什么没证明 |
| 开发助手指令 | `.agents/skills/<name>/SKILL.md` | 何时调用、按什么步骤检查 |
| 导航 | [docs/README.md](../README.md)、根 README | 先读哪篇、每篇负责什么 |

表中的目录规范不要求预建空目录。当前编号手册、`tutorial/`、`interview/` 等上游材料保留位置，作为实现参考和深入学习资料；不为了统一目录批量搬家或复制内容。涉及其实现变化时，更新原主题或注明基线，不让两个“当前说明”互相冲突。

## 一个主题只维护一份当前结论

- 使用稳定文件名，日期写正文。一次事项的实施、审查、修正写回原主题，不创建 `design-v2-final` 等并行正本。
- 设计写当前采用的规则；指南写可执行步骤；记录保留实际过程与证据。它们互相链接，不复制整段设计或通过计数。
- 历史失败与已冻结材料不重写为成功；新结果追加日期、候选版本及变化原因。
- 独立需求或独立模块才新建文档。一个小字段修正只需更新相关段落；大设计按可独立理解的主题拆分。
- 新增/删除/改名时更新所有直接入口。文档标题和路径解释主题，不把代码目录本身当作业务解释。

## 如何写一份有用的设计

围绕本次变化按需说明以下内容，不要求每份短文填满模板：

1. **背景与范围**：用户任务、现有问题、期望结果、非目标及假设。
2. **已有行为**：真实文件与函数、调用链、目前限制；源码链接只证明读到的实现，不证明运行正确。
3. **方案比较**：至少比较有实际意义的选项，说明继续复用是否可行。按正确性、学习难度、维护量、验证条件和迁移代价分析，说明推荐理由及改变选择的条件。
4. **具体行为**：输入、处理、输出、失败处理。涉及 API 写校验与权限；涉及数据写事务与约束；涉及任务写合法状态、重启、重试与外部结果未知处理。
5. **验收与落点**：每项关键行为对应实现位置、测试场景和可观察结果。拟新增文件或接口写“计划”，不提供尚不存在的运行命令。
6. **迁移与交付**：影响现有调用方时说明兼容、配置、数据迁移与撤回边界；未影响则简述即可。

以“工单创建”举例：模型负责整理客户诉求，规则判断订单和字段，授权人员批准写入。文档应解释批准针对哪一版草稿、重复请求如何识别、外部已成功但本地没收到回执时怎么处理。“使用 Agent + 数据库”不足以回答这些问题。

## 如何写指南与学习说明

指南先列前提与运行目录，再给最短操作、预期结果、常见失败和清理方式。示例必须能区分“预期”与“实际验证”；涉及收费或外部写入时说明目标与权限条件。

学习说明按下面顺序展开，短内容可合并：

> 业务问题 → 术语的白话解释 → 实际源码/函数 → 设计取舍 → 失败例子 → 小实验与预期结果 → 自检问题

- 初次讲 `Pydantic`，用“检查请求里有没有必填字段、类型对不对”解释，再链接 `ChatRequest`；不要只写框架名称。
- 初次讲“幂等”，用“客服点两次创建，只产生一张工单”解释；同时说明只保存本地键还不能证明外部系统不会重复创建。
- 初次讲“事务”，解释同一数据库里一组修改一起提交或一起撤回；明确它不能撤销已经发到外部系统的请求。
- 代码摘录只保留关键分支，附真实文件和函数名；行号会变化，不把硬编码行号当唯一定位方式。
- 从一个可检查的业务案例开始，不要求读者先学完整算法体系；深入原理链接既有教程。
- 每次完成一个功能，补它如何被调用、为什么这样设计、怎样验证。不要为凑学习材料复制全部源码。

## 状态与证据怎么写

| 标签 | 使用条件 |
|---|---|
| 计划/建议 | 尚未实现或尚未形成决定 |
| 已确认 | 有明确的需求或设计决定；不代表代码存在 |
| 已实现 | 当前版本有对应代码；不代表测试通过 |
| 已验证 | 指明版本、环境、命令、实际结果与未测范围 |
| 已推送 | 远端分支与文件回读一致；不代表部署 |
| 已试用/已部署 | 有对应用户使用或环境部署记录；二者仍需分别说明 |

演示数据、预期输出、上游历史测量和本 fork 实测必须标明。不得为了简历或介绍填写未测出的效率提升。原始日志与客户数据不默认入 Git，记录保留精简结论和可访问的证据位置；敏感字段先脱敏。

## 交付前检查

运行 `python3 scripts/check_project_docs.py`、`git diff --check`。检查器只覆盖项目维护文档和本次开发技能的结构、本地链接与元数据，不抓取外部 URL，不验证语义、命令可运行性或业务效果。没有链接错误也可能解释错了，需要再人工核对。

用 [文档审查清单](../../.agents/skills/dtc-documentation/references/review-checklist.md) 检查正文：新人能否说清一次请求经过哪些步骤、模型/规则/人工各负责什么、哪里看实现、哪里做实验、什么还没有完成。最终答复给出明确阅读顺序。
