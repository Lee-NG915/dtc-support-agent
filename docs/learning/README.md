# 从前端经验开始理解售后 Agent

更新日期：2026-11-03。这里是学习路线与静态源码练习；应用改造尚未开始，下面的实验预期不是已执行结果。

## 先想清楚谁在用

我们的首期产品服务企业内部客服与审批人。客户提出“商品破损想退货”，客服把诉求带入工作台，系统帮他找订单、查政策、整理草稿，再由有权限的人决定是否建立售后工单。

这条目标流程是：**查询资料 → 展示依据 → 形成草稿 → 人工批准 → 创建工单 → 核对结果**。消费者自动回复、真实退款和自动取消订单不在首期。具体范围以 [项目方案](../project-plan.md) 为准。

你的前端经验直接用于把订单信息、政策依据、草稿差异、审批和失败状态展示清楚。后端和 Agent 的学习围绕这些可见行为逐步展开。

## 先读哪几篇

1. 读项目方案的背景、范围和模型/规则/人工分工，先理解业务。
2. 做本页的“跟踪一条请求”练习，理解已有代码如何连接。
3. 按下面的学习顺序补一小块概念，再做一个能验证的功能。
4. 开发与写作时遵循 [文档规范](../guides/documentation.md)；需要助手协助时看 [技能指南](../guides/skills.md)。

上游教程保留为深入资料，不要求按它的完整理论顺序读完才开始。模型评测的专业知识可以逐步学习，但从第一个样例就要说清什么结果算正确。

## 跟踪一条已有请求

当前静态调用入口是：

```text
HTTP /chat → ChatRequest 校验 → 路由 chat() → ChatService.chat() → 业务处理与 Graph
```

这是一条查代码的线索，不代表每个请求都必经同一 Graph 节点；确认动作、拒绝和流式接口需继续看各自分支。

| 看哪里 | 要回答的问题 |
|---|---|
| [app/schemas/chat.py](../../app/schemas/chat.py) 的 `ChatRequest` | 请求里有哪些字段？什么会被拒绝？ |
| [app/api/routes/chat.py](../../app/api/routes/chat.py) 的 `chat` | 校验后的请求交给谁？返回值是什么？ |
| [app/services/chat_service.py](../../app/services/chat_service.py) 的 `ChatService` | 会话、待确认动作和业务处理在哪里协调？ |
| [app/agents/graph.py](../../app/agents/graph.py) 的 `build_graph` | 步骤怎样连接？现有图有没有持久恢复配置？ |
| [app/tools/registry.py](../../app/tools/registry.py) 与 [permissions.py](../../app/tools/permissions.py) | 工具如何找到？调用前检查什么？ |

**不用启动服务的第一项练习**：打开 `ChatRequest`，找到 `message` 与 `user_id`，再打开路由 `chat()`。

预期你能从代码说出：`message` 的长度限制是 1～4000；没有传 `user_id` 时使用 `anonymous`；路由把 `payload` 交给 `container.chat_service.chat`。进一步思考：字符串符合长度规则，是否说明这个人已被系统认证？答案是否定的，格式校验与身份验证是两件事。

这项练习只验证你能读懂代码条件。若要验证 HTTP 状态码，应先按 [快速开始](../02-getting-started.md) 安装环境，再增加或运行对应接口测试；本次没有执行 HTTP 实验。

## 把陌生词放回业务里

| 词 | 白话解释 | 在工单案例中的用途 |
|---|---|---|
| FastAPI | 接收 HTTP 请求并把它交给 Python 函数的框架 | 客服点击查询，后端找到相应处理函数 |
| Pydantic / Schema | 检查数据形状、类型和约束的模型 | 工单必须有订单号；字段合法仍需再检查权限 |
| SQL / 数据库 | 用表保存数据，并按条件读写 | 保存任务、批准内容和工单编号，服务重启后仍可读取 |
| 鉴权 | 判断这个已识别的人能不能执行这件事 | 客服只能查看有权限的店铺；不是信任浏览器传来的角色 |
| 异步 | 等网络或数据库时，让程序有机会处理其他工作 | 类似 JS 的 `await`；不会自动变成可靠的后台任务 |
| 事务 | 同一数据库的一组修改一起提交或撤回 | 任务与初始事件一起保存；不能撤回外部已创建的工单 |
| pytest | Python 自动测试工具 | 给定订单条件，检查规则和 API 返回是否符合预期 |
| 结构化输出 | 让模型按约定字段给结果 | 输出原因、订单号、建议；字段齐全不等于内容真实 |
| 上下文 | 当前交给模型处理的信息 | 客户诉求、相关政策和必要订单信息，避免无关内容挤满输入 |
| RAG / 检索 | 先找到资料，再依据资料组织回答 | 回答退货问题时给适用政策；找到资料不等于用对条款 |
| 工具调用 | 模型提出调用程序的名称和参数，由系统校验执行 | 查询订单或准备工单；模型不能自行授予权限 |
| 评测集 / 基线 | 固定的一组任务，以及最初版本在这些任务上的结果 | 同一批任务比较改动前后；不能每次换题宣称变好 |
| 状态机 | 给任务规定可处状态与允许的跳转 | 未批准的草稿不能直接变成已创建工单 |
| Worker / 后台工作进程 | 专门领取和处理任务的程序进程 | 客服关闭网页后仍可继续处理；可靠恢复还需要数据库记录 |
| Connector / 连接适配器 | 把外部系统操作封装成项目统一接口的代码 | 用相同的查询方式连接 Fake 数据或后续授权测试系统 |
| 检查点 | 保存已经做到哪一步和必要中间结果 | 重启后知道从哪里继续；不单独保证不会重复外部操作 |
| 幂等 | 同一业务操作重发后仍只产生约定的一份结果 | 双击创建或网络重试，不能多建工单 |
| 重试 / 对账 | 再尝试暂时失败的工作；核对不确定操作的实际结果 | 超时后先查是否已建单，不能假设失败后无限重发 |
| Docker / Linux | 打包运行环境的工具 / 常见服务器操作系统 | 让服务在另一台机器可运行；仍需要配置、数据库和网络 |
| 日志 / 健康检查 | 记录发生了什么 / 检查服务是否能响应 | 查清请求卡在哪层；进程健康不等于工单业务成功 |
| 数据库迁移 | 按版本改变表结构与数据 | 新增审批字段时，让已有数据库升级到新结构 |

## 按可验证功能推进

以下是学习与实现建议，尚未完成。每次只推进一个可观察行为，顺序与 [M1～M6](../project-plan.md#8-分阶段推进) 对齐。

| 顺序 | 要做的一件事 | 需要学什么 | 预期验证方式 | 进一步读 |
|---|---|---|---|---|
| 1 | 跑通基线，解释一次请求 | Python 基础、类型、FastAPI、Pydantic、pytest | 正常输入与无效输入有明确结果；记录初始案例 | [快速开始](../02-getting-started.md)、[API](../06-api-reference.md) |
| 2 | 从 Fake 数据查询一个订单 | SQL、仓储、异步、服务端身份与权限 | 查得到、查不到、无权限三种结果；不泄露其他店铺数据 | [架构](../03-architecture.md)、[安全](../09-security.md) |
| 3 | 为订单找到适用政策并生成草稿 | 检索、上下文、结构化输出、参数校验 | 依据支持结论；缺信息时澄清，不能编造订单 | [检索](../15-ingest-and-retrieval.md)、[工具](../05-agents-and-tools.md) |
| 4 | 保存审批并在重启后继续 | 数据建模、事务、状态机、检查点 | 同一草稿版本才可执行；拒绝和过期不能放行 | [可靠性参考](../08-reliability.md) 与项目方案的目标设计 |
| 5 | 在失败后避免重复建单 | 幂等、有限重试、回执、对账 | 双击与超时注入后只有一份业务结果，未知结果转人工 | [测试设计参考](../../.agents/skills/dtc-scoped-validation/references/test-design.md) |
| 6 | 比较一次有理由的改进 | 固定数据、基线、错误分类、人工评分、成本 | 同一组任务给分子/分母，报告剩余失败 | [评测](../10-evaluation.md) |
| 7 | 在干净环境部署并排障 | Docker、Linux、迁移、日志、健康检查 | 按指南启动，并定位一个人为注入的依赖故障 | [部署](../11-deployment.md)、[排障技能](../../.agents/skills/dtc-troubleshooting/SKILL.md) |

第 1 步就保留少量业务样例和人工处理基线，第 3～5 步持续补充。第 6 步才系统比较版本，避免把评测拖到所有功能写完。

## 每完成一小步留下什么

在同主题文档补充五件事：输入与结果、关键函数、设计理由、如何验证、剩余问题。原始输出不必全部放 Git，结果要能对应运行记录。

自检时尝试不用框架名回答：这个功能帮客服少做哪一步？什么由规则决定？哪一步需要人工？服务中断后会怎样？如果模型说错了，哪项测试或评测会发现？

下一步是 M1 的基线复现与 10 个种子案例，不是一次性实现整套后台。当前学习材料不意味着新接口、Worker、真实客服接入或业务收益已经完成。
